## Type Aware Rules

Some of the strongest TypeScript lint rules require type information — they need to resolve what a value actually is at runtime, not just what its local syntax looks like. Opt into [type-aware linting](https://typescript-eslint.io/linting/typed-linting/) by pointing at your `tsconfig.json`:

```ts title="eslint.config.ts"
import pleaseai from '@pleaseai/eslint-config'

export default pleaseai({
  typescript: {
    tsconfigPath: 'tsconfig.json',
  },
})
```

:::warning
Type-aware linting is slower than syntax-only linting because ESLint has to build a TypeScript program for every run. Start with it on small/medium projects; for very large monorepos consider scoping it to a subset of files.
:::

## Config Composer

`pleaseai()` returns a [`FlatConfigComposer`](https://github.com/antfu/eslint-flat-config-utils#composer), so you can fluently override, prepend, remove, or rename named config blocks when the plain options object isn't granular enough:

```ts title="eslint.config.ts"
import pleaseai from '@pleaseai/eslint-config'

export default pleaseai()
  .prepend(
    // flat configs before the main PleaseAI config
  )
  .override('antfu/stylistic/rules', {
    rules: {
      'style/generator-star-spacing': ['error', { after: true, before: false }],
    },
  })
  .renamePlugins({
    'old-prefix': 'new-prefix',
  })
  .remove('antfu/stylistic')
```

Reach for this API when:

- You want to **remove** a named config block entirely
- You need to **rename** a plugin prefix without writing a custom config
- You want to **override** rules inside a specific named block (more surgical than the top-level `overrides`)

## `command` Codemods

`@pleaseai/eslint-config` ships [`eslint-plugin-command`](https://github.com/antfu/eslint-plugin-command) — an on-demand micro-codemod system triggered by triple-slash comments. It's not a typical lint rule; you explicitly opt in per-site.

Built-in triggers include:

- `/// to-function` — arrow function → `function` declaration
- `/// to-arrow` — `function` declaration → arrow function
- `/// to-for-each` — `for` loop → `.forEach()`
- `/// to-for-of` — `.forEach()` → `for-of`
- `/// keep-sorted` — sort the next object/array/interface

See the [plugin docs](https://github.com/antfu/eslint-plugin-command#built-in-commands) for the full catalogue.

Usage — place the trigger one line above the code:

```ts title="before.ts"
/// to-function
const greet = async (name: string): Promise<void> => {
  console.log(`Hello, ${name}`)
}
```

After `eslint --fix`:

```ts title="after.ts"
async function greet(name: string): Promise<void> {
  console.log(`Hello, ${name}`)
}
```

The trigger comment is one-off — it's removed along with the transformation.

## Anti-slop Rules

`antislop` turns on rules from [`eslint-plugin-slop`](https://github.com/antfu/eslint-plugin-slop) and a curated subset of [`eslint-plugin-sonarjs`](https://github.com/SonarSource/SonarJS) through `@antfu/eslint-config`'s `antislop` option. Both plugins are optional peer dependencies:

```bash
bun add -D eslint-plugin-slop eslint-plugin-sonarjs
```

When you leave `antislop` unset, each plugin's rules turn on if that plugin is installed. Upgrading without the plugins changes nothing, and `please-style` installs both for new projects.

`antislop: true` requires both plugins. An object requires each plugin it turns on explicitly (`slop: true` or `slop: { ... }`; a numeric `cognitiveComplexity` turns on `sonarjs`), and a plugin it does not mention follows what is installed. An object that ends up turning on neither plugin leaves antislop off. A missing required plugin throws: `` `antislop` requires `eslint-plugin-sonarjs`. Install with `bun add -D eslint-plugin-sonarjs`, or set `antislop: false`. `` Turn off one part with `{ sonarjs: false }` or `{ slop: false }`, or everything with `false`.

```js
import pleaseai from '@pleaseai/eslint-config'

export default pleaseai({
  antislop: { cognitiveComplexity: 20 },
})
```

- `cognitiveComplexity` sets the `sonarjs/cognitive-complexity` threshold (default 15). `false` disables it.
- `slop: { cwd, inspection }` sets which changes the `slop` rules report: the whole file, uncommitted lines, or lines from recent commits. `inspection` is `'full'` (default), `'uncommitted'` or `'recent-changes'`. Keep `'full'` in CI: the other modes depend on git state (shallow clones, clean checkouts) and give different results locally and in CI.
- `slop/no-em-dash` is a warning in Markdown files and an error elsewhere. It has no autofix.
- On non-JS files (CSS, HTML, Vue, JSON, YAML, TOML, Markdown, and so on), the rule runs only where another config already parses them. Enabling `antislop` never makes ESLint lint new file types, so you get no parsing errors on CSS or HTML.

When this repository first turned antislop on, it reported 193 findings: 174 `slop/no-em-dash` (136 in Markdown), 8 `sonarjs/cognitive-complexity`, 7 `slop/prefer-jsdoc` (autofixable), 3 `slop/max-comment-length` and 1 `slop/no-trivial-functions`. They are fixed, and this repository now lints itself with antislop on. See [issue #76](https://github.com/pleaseai/code-style/issues/76) for the measurements.

## Quality Rules

`quality: true` turns on 12 `quality/*` rules from [anti-slop](https://github.com/dmmulroy/anti-slop), vendored through [`@nkzw/oxlint-config`](https://github.com/nkzw-tech/oxlint-config). They flag low-evidence typing and code patterns: a known value widened to `unknown` and asserted back, chained type assertions, `unknown` returns and type aliases, unsafe dictionary value types, `object` parameters, adjacent `filter`/`map` passes, reducer accumulator copies, `Reflect.get` / `Reflect.apply`, and conditional empty-object spreads. The option is off by default and needs no extra packages.

```js
import pleaseai from '@pleaseai/eslint-config'

export default pleaseai({
  quality: true,
  rules: {
    'quality/no-object-parameters': 'off',
  },
})
```

- Every rule is an error on JS and TS files. Code blocks in Markdown are skipped.
- `no-object-parameters` and `no-unknown-returns` are the most opinionated. Turn them off in `rules` if they do not fit your code.
- `quality/no-chained-type-assertions` reports the same code as `slop/no-chained-type-assertions` from `antislop`. If both are on, turn one off.
- None of the rules has an autofix.

With `quality: true`, this repository reports 29 findings: 13 `no-known-value-widening`, 10 `no-array-filter-map`, 3 `no-unsafe-dictionary-type`, 2 `no-conditional-empty-object-spread` and 1 `no-unknown-returns`. A larger private monorepo (2,669 files) reports 4,396 findings in 1,172 files, 61% of them in tests. The most frequent are `no-chained-type-assertions` (1,282), `no-unsafe-dictionary-type` (1,240), `no-known-value-widening` (745) and `no-conditional-empty-object-spread` (658). That volume is why the option is off by default. See [issue #77](https://github.com/pleaseai/code-style/issues/77).

## Plugins Renaming

`@pleaseai/eslint-config` inherits `@antfu/eslint-config`'s plugin renaming for a shorter, consistent DX:

| New prefix | Original prefix | Source plugin |
| --- | --- | --- |
| `import/*` | `import-lite/*` | [`eslint-plugin-import-lite`](https://github.com/9romise/eslint-plugin-import-lite) |
| `node/*` | `n/*` | [`eslint-plugin-n`](https://github.com/eslint-community/eslint-plugin-n) |
| `yaml/*` | `yml/*` | [`eslint-plugin-yml`](https://github.com/ota-meshi/eslint-plugin-yml) |
| `ts/*` | `@typescript-eslint/*` | [`@typescript-eslint/eslint-plugin`](https://github.com/typescript-eslint/typescript-eslint) |
| `style/*` | `@stylistic/*` | [`@stylistic/eslint-plugin`](https://github.com/eslint-stylistic/eslint-stylistic) |
| `test/*` | `vitest/*` | [`@vitest/eslint-plugin`](https://github.com/vitest-dev/eslint-plugin-vitest) |

So when you override a rule, use the new prefix:

```ts title="eslint.config.ts"
import pleaseai from '@pleaseai/eslint-config'

export default pleaseai({
  rules: {
    'ts/consistent-type-definitions': ['error', 'interface'],
    'style/max-statements-per-line': ['error', { max: 2 }],
  },
})
```

## View Enabled Rules

Use [`@eslint/config-inspector`](https://github.com/eslint/config-inspector) to visualise the fully-resolved config in a browser — every enabled rule, every plugin, every file glob:

```bash title="Terminal"
npx @eslint/config-inspector
```

It opens a local server showing the flat config graph. Indispensable when you're debugging "why is this rule firing" or "which preset added this".

## Re-exports

Every export from `@antfu/eslint-config` is re-exported, so you can import fine-grained configs directly when you want to compose them by hand instead of using the `pleaseai()` factory:

```ts title="eslint.config.ts"
import { combine, javascript, typescript, vue } from '@pleaseai/eslint-config'

export default combine(
  javascript(),
  typescript(),
  vue(),
)
```

## Versioning Policy

`@pleaseai/eslint-config` follows [Semantic Versioning](https://semver.org/), but because it's an opinionated style preset with many moving parts, **rule changes are not treated as breaking changes**.

**Breaking (major bump)**

- Node.js version requirement changes
- Large refactors that may break downstream configs
- Major plugin upgrades that may break existing rules
- Changes that likely affect most codebases

**Non-breaking (minor/patch)**

- Enabling or disabling individual rules (even if stricter)
- Changing rule options
- Dependency version bumps

If a rule tightening breaks your build, pin to the previous minor version and [open an issue](https://github.com/pleaseai/code-style/issues) so we can discuss the trade-off.
